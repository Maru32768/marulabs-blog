# 設計判断の記録

前提、判断理由、代替案を残します。状況が変わったら更新してください。

## 技術スタック

### Astro 7 の Markdown プロセッサに `unified()` を使う

- **判断:** 既定の Sätteri ではなく、`@astrojs/markdown-remark` の `unified()` を使う。
- **理由:** コードブロックの見出し、Quote、メモ/注意、表の見出しに rehype プラグインと Shiki の transformer が必要。`unified()` の経路ではソースで動作を確認できた。Sätteri は `shikiConfig` の扱いがドキュメントに明記されていない。
- **トレードオフ:** ビルドは Sätteri より遅い可能性があるが、小規模なブログでは問題にならない。
- **再検討の条件:** `unified()` のサポートが縮小されたら、`src/plugins/` を Sätteri の hast プラグインへ移植する。

### TypeScript は 6 系、Vitest は 4 系

- **判断:** 最新の TypeScript 7 と Vitest 5 は使わない。
- **理由:** `@astrojs/check` が `^5 || ^6`、`typescript-eslint` が `<6.1.0` を要求する。Vitest は `@cloudflare/vitest-plugin` が 5 にも対応しているが、4 で動作確認済み。
- **再検討の条件:** 上記のツールが TypeScript 7 に対応したら上げる。

### Workers Static Assets を使う（Pages ではなく）

- **理由:** Cloudflare は新規プロジェクトに Workers を推奨している。静的アセットへのリクエストは無料かつ無制限で、Worker が動くのは `run_worker_first` に指定した `/api/*` だけ。
- **帰結:** Worker やカウンターが落ちても記事は配信され続ける。

### Astro の Cloudflare アダプターは使わない

- **理由:** 全ページが静的生成なので不要。公式ガイドでも静的サイトにアダプターは不要とされている。カウンター API は `worker/index.ts` に独立して置く。

## 公開境界

### Public と Private を別リポジトリにする（`.gitignore` に頼らない）

- **理由:** Public リポジトリのビルドと CI が、Private の内容へ物理的に到達できない構成にするため。サブモジュールも使わない。
- **補強:** `articleSchema` は `strictObject` で、`draft` や `status` のようなキーがあるとビルドが失敗する。「未公開」という状態を Public リポジトリに持ち込ませない。

### ビルド成果物は許可リストで検査する

- **判断:** `verify-dist` は既知の悪いパターンを探すのではなく、記事ページ・RSS・Atom・サイトマップ・Pagefind 索引のそれぞれが「公開記事の slug の集合」と完全に一致することを確認する。
- **理由:** 想定外の混入は名前を予測できない。Pagefind の索引は圧縮されたフラグメントを展開して検査する。

### テストフィクスチャはデプロイできない出力先へビルドする

- **判断:** `BLOG_CONTENT=fixtures` は `dist-fixtures/` に出力し、キャッシュも分ける。`wrangler.jsonc` が配信するのは `dist/` だけ。
- **代替案:** 環境変数で任意のディレクトリを指定できる構成は、不注意で別の場所を公開できてしまうので採用しない。

### 公開記事 0 件で立ち上げる

- **判断:** 最初のデプロイに記事を含めない。Claude が書いた記事を Public に置くことは「明示的な指示なしに公開しない」というルールに反するため。最初の記事は Private の Draft として用意し、公開は管理人が判断する。
- **帰結:** すべてのページは 0 件でも正しく表示される。Pagefind は空の索引を作れないので、記事がなければ索引を作らず、検索ページが案内を表示する。
- **検証への影響:** 検索や記事の表示はフィクスチャのビルドで検証している。実際の記事での確認は最初の公開時になる。

### プレビューは Version URL を使う

- **判断:** PR ごとに `wrangler versions upload --preview-alias pr-N` を実行する。同じリポジトリからの PR に限る。
- **公開境界:** プレビューにも `verify` ジョブで検査した同じ `dist` を使う。そもそも PR の内容は Public リポジトリ上で公開済み。
- **注意点:** Version URL は本番のバインディング（D1）を共有する。Worker は `COUNT_HOST` 以外のホストでは数えない。URL は公開されるが、全ページの canonical が本番を指す。
- **前提:** Version URL にはアカウントの `workers.dev` サブドメインが必要。Worker の `workers_dev: false` とは別の設定で、未登録だと URL が発行されない（2026-11-08 に確認）。
- **代替案:** Workers Previews は独立した環境を作れるが、この規模では設定が増えるだけなので使わない。

## インフラ

### Terraform と Wrangler の責務分担

| 対象                                     | 管理する側 | 理由                                                     |
| ---------------------------------------- | ---------- | -------------------------------------------------------- |
| Worker 本体（コードなし）                | Terraform  | 公式が推奨する `cloudflare_worker` の使い方              |
| D1 データベース                          | Terraform  | `prevent_destroy` でカウンターの値を守る                 |
| カスタムドメイン                         | Terraform  | DNS レコードと証明書は Cloudflare が自動で作成・管理する |
| 既存 Zone                                | 参照のみ   | データソースで読むだけ。変更しない                       |
| コード、静的アセット、バージョン         | Wrangler   | デプロイのたびに変わるもの                               |
| バインディング（D1、レート制限、ASSETS） | Wrangler   | 下記を参照                                               |
| D1 のスキーマ                            | Wrangler   | `migrations/` をマイグレーションとして適用する           |

- **依頼内容との差分:** 依頼には「バインディング等のインフラ設定」を Terraform で管理する例が挙がっていたが、バインディングは Worker のバージョンの属性で、Terraform で持つにはコードのアップロードも Terraform が担当する必要がある。ビルドした Worker と静的アセットを Terraform で扱うと、記事の公開のたびに Terraform が動く。そのためバインディングは `wrangler.jsonc` に置いた（Git で管理される点は同じ）。D1 の ID だけ Terraform の出力から転記する。
- **DNS レコード:** カスタムドメインが自動で管理するので、Terraform の `cloudflare_dns_record` は作らない。`wrangler.jsonc` にも `routes` を書かない。
- **`workers_dev` と `preview_urls`:** Terraform と Wrangler の両方に同じ値を書いている。片方だけ変えると差分が出るので、変更するときは両方を変える。

### Terraform の state は R2 に置く

- **判断:** Cloudflare R2 の非公開バケットを S3 互換バックエンドとして使う。`use_lockfile = true` で排他制御する。バケットは Terraform の外で作る（state を置く場所を Terraform で管理すると循環するため）。
- **認証情報:** mise の `ops` プロファイルが環境変数で渡す。リポジトリには置かない。アカウント ID も `AWS_ENDPOINT_URL_S3` で渡すので、リポジトリに現れない。
- **state の中身:** このスタックの state に API トークンや秘密値は入らない。それでも ID などの情報を含むので Public リポジトリには置かない。
- **代替案:** HCP Terraform は外部サービスへの依存が増える。ローカル state はマシンの故障で失う。
- **確認したこと:** HashiCorp は S3 バックエンドを Amazon S3 に対してのみテストしているが、R2 でも state の保存とロックの取得・解放が動くことを 2026-11-08 に実機で確認した。

### Terraform の plan と apply は CI で実行しない

- **理由:** Public リポジトリの Actions のログは誰でも読める。plan の出力に ID などが残り、state と強い権限のトークンを CI に置くことにもなる。インフラはほとんど変更しないので、CI は `fmt` と `validate` だけにして、管理人のマシンで実行する。
- **トレードオフ:** ドリフトの自動検出はなくなる。

### GitHub Actions のトークンを 2 つに分ける

- **判断:** CI に渡すのはデプロイ用の最小権限トークン（Workers Scripts と D1 の編集）だけ。Zone や DNS の権限は Terraform 用のトークンにのみ付ける。
- **理由:** Public リポジトリの CI が漏れても、既存の DNS 設定には触れられないようにするため。

## 配信

### Cloudflare の解析スクリプトをこのサイトでは止める

- **事象:** `marulabs.dev` のゾーンで Web Analytics の自動挿入が有効で、本番の HTML に `cloudflareinsights` のスクリプトが挿入された。ブラウザから見たリクエストにだけ挿入されるので、ローカルや `curl` のテストでは見つからなかった。CSP がブロックするのでデータは送られないが、全ページでコンソールエラーが出て、サイトの「解析タグなし」という記述とも食い違う。
- **判断:** ページの応答に `Cache-Control: no-transform` を付ける（`public/_headers`）。ゾーンの設定は他のサイトにも効くので変えない。
- **トレードオフ:** エッジでの圧縮も止まるので、HTML の転送量が増える（実測: トップページ 4.8 KB → 25.4 KB）。CSS、JS、RSS などは圧縮されたまま。
- **代替案:** Configuration Rule の `disable_rum` なら圧縮を維持できるが、トークンに `Zone > Config Rules > Edit` を足し、ゾーンの `http_config_settings` フェーズ全体を Terraform で所有する必要がある。既存のルールを消す恐れがあるので先に中身を確認すること。HTML の圧縮が問題になったら移行する。
- **既知の制限:** `_headers` で末尾スラッシュのないパスを表せないので、`/nope` のような URL の 404 ページには挿入される（CSP がブロックする）。
- **再発の検知:** `scripts/smoke-test.ts` がブラウザと同じヘッダーでリクエストして、スクリプトがないことを確認する。

### 平文の HTTP をリダイレクトしない

- **理由:** `.dev` は HSTS preload の対象なので、主要なブラウザは常に HTTPS で接続する。リダイレクトするゾーン設定（Always Use HTTPS）は他のサイトにも効くので変えない。

## 命名

サイトの表示名は変わる可能性があるので、インフラの名前には使わない。

| 名前                              | 対象                   | 理由                                                                 |
| --------------------------------- | ---------------------- | -------------------------------------------------------------------- |
| `Maru's Blog`                     | サイトの表示名         | `src/data/site.ts` の 1 箇所だけに書く。変えてもインフラに影響しない |
| `marulabs-blog`                   | リポジトリ、Worker、D1 | ドメイン `blog.marulabs.dev` に対応する。表示名には合わせない        |
| `marulabs-blog-tfstate`           | R2 バケット            | 他のプロジェクトと共有しない。トークンをバケット単位で絞れる         |
| `~/.config/marulabs-blog/ops.env` | 秘密情報               | `marulabs` だけだと同じドメインの別プロジェクトと被る。`ops` と対応  |
| `4771`                            | レート制限の namespace | アカウント全体で共有される値なので、公式の例の `1001` を避ける       |

## ツールと環境変数

### mise で管理する

- **判断:** ツールのバージョンと環境変数を mise に一本化する。`.mise.toml` に「どこまで自動で上げてよいか」、`mise.lock` に正確なバージョンとチェックサムを書く。CI も `jdx/mise-action` と `MISE_LOCKED=1` で同じものを使う。
- **理由:** ローカルと CI でバージョンが食い違わない。`.nvmrc` や CI の Terraform のバージョン指定のように、複数の場所に書かずに済む。
- **確認したこと:** グローバル設定のない環境でも、範囲指定（`terraform = "1"`）より `mise.lock` が優先される。ロックを改ざんするとインストールが失敗する。
- **トレードオフ:** `setup-node` の npm キャッシュを使わなくなるので、CI の `npm ci` は少し遅くなる。

### 秘密情報は `ops` プロファイルを指定したときだけ読み込む

- **判断:** 秘密情報をリポジトリの外の `~/.config/marulabs-blog/ops.env` に置き、`.mise.ops.toml` から読み込む。`mise -E ops exec -- <コマンド>` のときだけ環境変数になる。
- **`.env` を使わない理由:** 実際に試すと、Astro は `.env` の値を `import.meta.env` でページから読め、静的 HTML に出力できた。Wrangler は `.env` の `CLOUDFLARE_API_TOKEN` を読んで API へ送った。公開サイトのリポジトリでは危険なので、他のプロジェクトの慣例（`.mise.toml` の `_.file = ".env"`）に揃えていない。
- **プロファイルを分ける理由:** 常に読み込むと、Terraform 用の強いトークンが `npm ci` のときに依存パッケージのスクリプトへ渡る。必要なコマンドにだけ渡す。
- **トレードオフ:** コマンドが長くなる。ファイルは暗号化されていない（パーミッション 600 のみ）。`redact` が効くのは `mise run` の出力で、`mise exec` の出力や `mise env` は隠されない。
- **代替案:** SOPS や fnox で暗号化すれば Git で管理できるが、1 人の運用には鍵の管理が増えるだけなので採用しない。

## アクセスカウンター

### 1 行のカウンターを D1 に持つ

- **判断:** `UPDATE ... SET value = value + 1 ... RETURNING value` で加算する。
- **整合性:** D1 の単一プライマリで原子的に加算するので、取りこぼしも二重加算もない。
- **料金:** 1 PV が 1 行の書き込み。無料枠は 1 日 10 万行、読み取りは 1 日 500 万行。個人ブログには十分で、超えた場合はカウンターが止まるだけで記事は読める。
- **代替案:** Workers KV は結果整合で同時更新に弱い。Durable Objects はこの用途には大げさ。

### IP アドレスを一切読まない

- **判断:** サーバーは IP アドレスを読まず、保存もしない。レート制限のキーは定数（`pageviews`）。
- **理由:** 公式ドキュメントも IP アドレスをレート制限のキーにすることを推奨していない。「永続保存しない」より強い「読まない」を選ぶと、説明も検証も単純になる。
- **トレードオフ:** 1 人の悪用者を個別に止められない。上限はロケーションごとに毎分 60 件で、悪用されても数値が増えるのは最大でも 1 拠点あたり 1 日 8.6 万件程度。同時に正規の加算も止まるが、このカウンターは正確な統計ではなく飾りなので許容する。

### 多層の過剰カウント対策

| 層       | 対策                                                     | 防げるもの                 |
| -------- | -------------------------------------------------------- | -------------------------- |
| ブラウザ | POST はスクリプトからだけ送る                            | JS を実行しないクローラー  |
| ブラウザ | `navigator.webdriver` が真なら数えない                   | 自動化ブラウザ             |
| ブラウザ | 同じタブの同じページは 30 分間数えない（sessionStorage） | 再読み込みの連打           |
| Worker   | `COUNT_HOST`、`Origin`、`Sec-Fetch-Site` を確認          | 他サイトやプレビューから   |
| Worker   | User-Agent で既知のボットを除外                          | 名乗っているボット         |
| Worker   | レート制限 60 件/分/ロケーション                         | 上記をすり抜けた機械的連打 |

ヘッダーは偽装できるので完全な防御ではない。目的は「基本的な対策」であり、正確な統計ではない。

### Workers Logs を無効にする

- **理由:** カウンターの運用に要求メタデータの保存は不要。`observability.enabled = false` にしている。

## デザインからの変更

### 依頼に沿って削除したもの

- 前回の訪問、それ以降の新着件数、既読にする、すべて既読にする
- PC版レイアウトへのリンク（レスポンシブなので不要）
- Lab Status。中身がすべてダミーで、特に「下書き」欄は未公開の記事名を公開してしまうため。

### 文言を削ったもの

シンプルで飾らない方向にするため、キャッチコピーの類を消した。

- ヘッダーのタグラインと説明文、トップページのようこそ文、プロフィールの決まり文句
- ページタイトルの副題、OGP 画像の文言

RSS と検索エンジンには説明が必須なので、`site.description` に事実だけを書いた 1 行を残している。ページには表示しない。

### データに合わせて変えたもの

| デザイン                           | 実装                                    | 理由                                       |
| ---------------------------------- | --------------------------------------- | ------------------------------------------ |
| 記事数、改訂数、更新履歴           | Markdown から生成                       | ダミーを表示しない                         |
| 開設 2019/04、© 2019–              | 2026/11、© 2026                         | 実際の開設時期                             |
| サブカテゴリ                       | カテゴリ内で多いタグ（表示は「タグ:」） | 架空の分類を作らない                       |
| 新着（前回の訪問以降）             | 14 日以内に更新                         | 閲覧者の状態を持たずに日付だけで判定       |
| 連載の「執筆中」「予定」           | 公開済みの回だけ表示                    | 未公開の予定を出さない                     |
| Mail リンク                        | GitHub Issues                           | メールアドレスの公開は管理人が判断すること |
| 構成: 静的HTML（自作ジェネレータ） | 静的HTML（Astro / Cloudflare Workers）  | 事実に合わせた                             |
| バッジ html / by hand              | html / static                           | 事実に合わせた                             |

### 追加したもの

- **アクセスカウンター:** プロトタイプにはなかった。デザインの配色とベベル表現で作った。トップページと一覧ページのサイドバーに表示する。
- **小さなピクセル文字:** 80×15 のバッジは 8px のまま残した。読むための文字ではなく、当時のサイトを象徴する装飾だから。

### フォントサイズ

| 用途             | プロトタイプ | 実装      |
| ---------------- | ------------ | --------- |
| 記事本文         | 15–16px      | 17px      |
| コード           | 13px         | 14–14.5px |
| 通常の UI        | 12–13px      | 14–15px   |
| リストのタイトル | 13–14px      | 15–16px   |
| メタデータ       | 11px         | 13px      |
| タグ             | 10px         | 12px      |

サイドバーを 240px から 270px に、外枠を 1120px から 1180px に広げて、情報密度を保ったまま文字を大きくしている。
